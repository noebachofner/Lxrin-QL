# Audit history

`ch.lxrin:lxrin-ql-audit` keeps a full history of audited tables. For every row that is
inserted, updated or deleted, a copy goes to `<table>_aud` together with a revision
number and the kind of change. Each transaction gets one revision row with the time and
the user.

The default layout is the one of **Hibernate Envers**. Envers can read a history written
by LxrinQL, and LxrinQL can continue a history written by Envers. A project can therefore
run both on the same tables, or migrate from Envers step by step.

```kotlin
dependencies {
    implementation("ch.lxrin:lxrin-ql-audit:3.2.0")      // Groovy: implementation 'ch.lxrin:lxrin-ql-audit:3.2.0'
}
```

The module depends only on `lxrin-ql-core`.

## Tables

```sql
CREATE TABLE revision (
    id         bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    revised_at timestamptz NOT NULL,
    user_id    uuid
);

CREATE TABLE app_user_aud (
    id      uuid     NOT NULL,                              -- the key columns of app_user
    rev     bigint   NOT NULL REFERENCES revision (id),
    revtype smallint NOT NULL,                              -- 0 insert, 1 update, 2 delete
    name    text,                                           -- every other column, nullable
    email   text,
    …
    PRIMARY KEY (id, rev)
);
```

- An audit table has the columns of its table, all nullable, plus `rev` and `revtype`.
  Its primary key is the table's key plus `rev`, as Envers creates it.
- The revision number must be generated by the database (identity or serial).
- Columns you exclude (see below) must not exist in the audit table, or must be
  nullable.

## Without Spring

```java
AuditSettings settings = AuditSettings.builder()
        .tables("app_user", "asset")                           // by name or schema.name
        .tablePatterns("doc_.*")                               // or by regular expression
        .excludeColumns("app_user", "last_seen_at")            // not copied
        .user(AuditUser.of(SqlTypes.UUID, CurrentUser::id))    // stored in revision.user_id
        .build();

QueryContext ctx = QueryContext.builder()
        .dataSource(dataSource)
        .listener(new AuditListener(settings))
        .build();
```

| Setting | Default | Meaning |
|---|---|---|
| `tables(..)`, `tablePatterns(..)` | none | audited tables; audit tables and the revision table are never audited |
| `excludeColumns(table, ..)` | none | columns not copied, e.g. `last_seen_at` |
| `suffix(..)` | `_aud` | audit table = table name + suffix, in the table's schema |
| `storeDataAtDelete(..)` | `false` | `true`: delete rows contain the full row; `false`: only the key, like Envers |
| `revisionSchema/Table/IdColumn/TimestampColumn/UserColumn(..)` | default schema, `revision`, `id`, `revised_at`, `user_id` | the revision table |
| `revColumn(..)`, `revtypeColumn(..)` | `rev`, `revtype` | columns of the audit tables |
| `user(AuditUser)` | none | the user of each revision; without one, the user column is not written |
| `clock(..)` | UTC system clock | the revision time |

## With Spring Boot

With `lxrin-ql-audit` on the class path, `lxrin-ql-spring` creates the listener as soon as
tables are configured:

```yaml
lxrin:
  ql:
    audit:
      tables: app_user, asset
      table-patterns: doc_.*
      excluded-columns:
        app_user: last_seen_at
      store-data-at-delete: false
      suffix: _aud
      rev-column: rev
      revtype-column: revtype
      revision:
        table: revision
        id-column: id
        timestamp-column: revised_at
        user-column: user_id
```

```java
@Bean
AuditUser<UUID> auditUser() {
    return AuditUser.of(SqlTypes.UUID, CurrentUser::id);   // e.g. the Keycloak subject from Spring Security
}
```

- `lxrin.ql.audit.enabled=false` turns it off.
- A `Clock` bean, if there is one, supplies the revision time.
- Your own `AuditListener` bean replaces the one from the properties.
- For schema-qualified keys in `excluded-columns`, use brackets:
  `excluded-columns[public.app_user]`.

## What is audited

- **Every write path.** Repository writes (`save`, `saveAll`, `insert`, `update`,
  `delete`, `deleteById`, `deleteAll`), DSL statements, the
  `createInsert`/`createUpdate`/`createDelete`/`createUpsert` style, upserts (each row
  as an insert or an update) and soft deletes (as deletes). All of them go through the
  statement pipeline, which returns the full rows to the listener.
- **Same transaction.** The history is written in the same transaction as the change. A
  rollback leaves neither history nor revision. A revision created inside a savepoint
  that is rolled back is discarded, and the next change creates a new one.
- **One revision per transaction.** Several changes to one row in one transaction leave a
  single audit row with the latest state. An insert stays an insert, and a delete wins.
- **Exact copies.** Audit rows are written as they are: column conventions, table
  policies and the version column do not apply to them.
- **No `TRUNCATE`.** `TRUNCATE` of an audited table is rejected, because the rows would
  be missing from the history.

## Hibernate Envers

Configure Envers for the same layout:

```properties
org.hibernate.envers.audit_table_suffix=_aud
org.hibernate.envers.revision_field_name=rev
org.hibernate.envers.revision_type_field_name=revtype
```

and map the revision table as the revision entity:

```java
@Entity
@Table(name = "revision")
@RevisionEntity(UserRevisionListener.class)
public class Revision {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY) @RevisionNumber
    private Long id;
    @RevisionTimestamp @Column(name = "revised_at")
    private Instant revisedAt;
    @Column(name = "user_id")
    private UUID userId;
}
```

`AuditReader.getRevisions(..)`, `find(..)` and `forRevisionsOfEntity(..)` then see the
changes made through LxrinQL, and LxrinQL continues the history written by Envers.
[`EnversIT`](../integration-tests/src/test/java/ch/lxrin/ql/it/EnversIT.java) tests both
directions.

Differences from Envers: an insert and a delete of the same row in one transaction leave a
delete row, where Envers stores nothing. Envers features beyond this layout (the validity
audit strategy, modified flags, audited relations) are not written.
