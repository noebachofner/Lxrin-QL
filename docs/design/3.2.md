# LxrinQL 3.2 – Integration fixes, code generation without Docker, audit history

Status: **implemented** in 3.2.0. This note records the decisions that 3.2 adds to the
[3.0 design](3.0.md) and [3.1 design](3.1.md). The items come from integrating 3.0.1 and
3.1.0 into a Spring Boot 4 project (Groovy `build.gradle`, Flyway, PostgreSQL 18,
Hibernate Envers, a strict no-comments code policy).

Two changes are intentionally incompatible, and both are documented in the changelog and
the migration notes: the names of generated foreign key constants (item 1), and record
mapping by position (item 9). Everything else is additive.

## Decisions

| Topic | Decision | Reason |
|---|---|---|
| Foreign key constant | `FK_` + the upper-snake foreign key columns (`FK_CREATED_BY`, `FK_ORDER_ID_LINE_NO`). An override comes from `foreignKeyNames` (constraint name, or `table.constraint`, → constant). A collision with another key constant or a column constant is an error that names both keys | The name depends only on the key itself, so adding, removing or reordering other keys never renames it. Numbering (`_2`) would bring back the order dependence. |
| No comments | Comments are removed from the finished source with a small Java lexer that knows string, text-block and character literals. It is not a second set of templates | Every generator keeps a single template, so the two variants cannot drift apart. The `// Generated by LxrinQL codegen – do not edit.` header stays because stale-file detection needs it. Stubs never had a header. |
| `stubJavadoc` | Defaults to `generateJavadoc` | This is what the spec requires. Stubs belong to the developer, so they need their own switch. |
| `col(..)` | `<T> Field<T> col(Field<T> field)` returns its argument after a null check | It is a typed identity, so it keeps `T` and compiles in select and returning lists. |
| `QL` | A new public, non-final `ch.lxrin.ql.dsl.Statements extends Functions` holds all static methods that were declared in `Dsl`. `Dsl` and `ch.lxrin.ql.QL` both extend it and have private constructors. A test compares the public static methods of both classes | There is one implementation. Static calls compiled against 3.1 (`Dsl.selectFrom`) still resolve through the superclass, as with `Conditions` in 3.1. |
| Record mapping | By name only by default (column name or alias, `snake_case` = `camelCase`). If any component has no field, the statement fails when it is built, and the error lists every unmatched component and every unused field. Positional mapping only after `c.mapByPosition()` | This restores the 3.0 rule that reordering a select list must not silently change the result. Extra fields are allowed as long as every component is matched. |
| User conventions | `createdBy(column, type, Supplier<T>)` sets the column on insert; `updatedBy(..)` sets it on insert and update | The same as `createdAt` and `updatedAt`. |
| Snapshot file | JSON (`format`, `migrations` hash, enums, tables). One line per column and key, sorted as `pg_catalog` returns them (schema, name, `attnum`, constraint name), `\n` line endings. It is written and read without a JSON library | It is stable and easy to diff, and codegen gets no new dependency. |
| `schemaSource` | `database` (container or `jdbcUrl`), `snapshot`, or `auto` (the default). `auto` uses the database if a `jdbcUrl` is set or Docker is available, otherwise the snapshot, and logs which one it chose and why. It fails with a clear message if it can use neither | This is the behaviour the spec asks for. The Docker check is Testcontainers' own check. |
| Snapshot staleness | The snapshot stores a SHA-256 of the migration and script files (relative names and contents, line endings normalised). `generateLxrinQl` warns when the snapshot is used and the hash differs. `lxrinQlCheckSnapshot` reads the schema from the migrations and compares the complete snapshot text. Without Docker it compares only the hash and says so | CI gets a precise check. A machine without Docker still gets a useful one. |
| Audit module | `lxrin-ql-audit` (depends only on `lxrin-ql-core`): an `AuditListener` (a `StatementListener`) configured through `AuditSettings`. It reads the full row through `requestReturning`, so repository writes, DSL writes, the `create…` style and upserts are all covered | Every write already goes through the pipeline. This is the ISMS example from the integration tests, generalised. |
| Audit layout | Envers by default: `<table>_aud(<pk…>, rev, revtype smallint 0/1/2, columns…)` with primary key `(<pk…>, rev)`, one `revision(id, revised_at, user_id)` row per transaction. Table, column names and suffix are configurable. Several changes to one row in one revision leave one row with the latest state; `ADD` stays `ADD`, and `DEL` wins | Envers can read the history and keep writing to it, so a project can run both on the same history or migrate away from Envers. |
| Delete rows | Only the key columns by default. `storeDataAtDelete` stores the full row. Soft deletes are `DEL` rows | This matches Envers' `store_data_at_delete`. |
| Revision after a nested rollback | The revision id is kept per transaction and discarded when a savepoint that created it is rolled back | Otherwise a later change would reference a revision row that the rollback removed. |
| Current user | `AuditSettings.user(DataType<T>, Supplier<T>)`; in Spring, an `AuditUser` bean. Without one, `user_id` stays `NULL` | Who the user is depends on the application. |
| Spring | `lxrin.ql.audit.*` properties; the listener bean exists when `lxrin-ql-audit` is on the class path and `lxrin.ql.audit.enabled` is not `false` | This follows the auto-configuration style of 3.0. |
| Plugin Portal | Cause: the first submission of `ch.lxrin.ql.codegen` is waiting for approval by the portal team (see below). The workflow now checks the credentials first, and afterwards fetches the plugin marker POM from `https://plugins.gradle.org/m2/` **without following redirects**. It retries for ten minutes and fails unless the portal itself answers `200` | The portal answers requests for unknown plugins with a `303` redirect to Maven Central. A check that follows redirects would pass although the portal does not serve the plugin. |

## Gradle Plugin Portal findings

- `publish.yml` for v3.0.1 and v3.1.0: the step `publishPlugins` ran and succeeded in about
  four seconds. For v3.0.0 it failed after one second.
- `https://plugins.gradle.org/plugin/ch.lxrin.ql.codegen` says "Plugin Not Found", and the
  portal user `noebachofner` "has not authored any plugins yet".
- The marker `…/ch.lxrin.ql.codegen.gradle.plugin/3.1.0/…pom` on `plugins.gradle.org/m2`
  returns `404`, and `maven-metadata.xml` returns a `303` to Maven Central. A Gradle 9.7
  build with the default plugin repositories cannot resolve `ch.lxrin.ql.codegen:3.1.0`
  (verified).
- `publishPlugins` succeeds for a plugin ID whose first version is still waiting for manual
  approval. The portal also requires proof that you own the `ch.lxrin` namespace
  (`lxrin.ch`). This matches every observation above. Missing credentials would make the
  step fail, and a skipped step would not show as run.
- What the repository can fix, it now does: the credential check, the verification check,
  and a manual `workflow_dispatch` that publishes only the plugin for an existing tag. The
  approval itself has to be completed on the portal account (answer the portal's e-mail or
  verify the domain), and then v3.2.0 can be published again with that dispatch.

## Tests

- Codegen: foreign keys (self-reference, two keys to one table, a third key added, composite
  keys, collisions, overrides); both comment options (compiled, and no comment left in the
  output); snapshot round trip, stable output, `schemaSource` selection, hash check; CLI,
  Gradle plugin and Maven plugin options.
- Core: `QL` and `Dsl` expose the same static methods; `col(..)` in both styles; record
  mapping errors and `mapByPosition()`; user conventions.
- Integration: the audit module against PostgreSQL (every write path, rollback, nested
  rollback, excluded columns, delete data, patterns) and against Hibernate Envers in both
  directions; Spring auto-configuration; `createdBy` from the Spring Security context; a
  Groovy DSL consumer project; snapshot generation without a database; the portal check
  script against a local HTTP server.
