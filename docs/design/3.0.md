decisions from the review and the places where the implementation differs from the
draft are listed in [§19](#19-decisions-and-deviations). The user guides in `docs/`
describe the final API.
Scope: turn LxrinQL 2.0.0 (a string-friendly query builder) into a strongly
typed query language and data access layer for PostgreSQL, released as 3.0.0.

## 1. Analysis of 2.0.0

2.0.0 has 5.4k lines of main code in one module, 133 unit tests (all green)
and one PostgreSQL integration test that only runs when `LXRIN_QL_PG_URL` is
set.

### What is worth keeping

- **SELECT coverage**: CTEs (recursive, materialized, data-modifying),
  `DISTINCT ON`, all join types, grouping sets, `WINDOW`, set operations,
  `FETCH … WITH TIES`, row locking. The clause order and rendering rules in
  `AbstractSelect.renderBody` are correct and well tested.
- **DML coverage**: multi-row `INSERT`, `INSERT … SELECT`, upserts with
  `ON CONFLICT … WHERE`, `UPDATE … FROM`, `DELETE … USING`, `RETURNING`.
- **Safety nets**: `UPDATE`/`DELETE` without `WHERE` is rejected unless
  `allRows()` is called, and `eq(x, null)` is rejected.
- **The function catalog** (about 250 functions), including the tricky ones:
  JSON key tests as functions so `?` does not clash with JDBC, validated
  `cast` type names, and literal quoting.
- **Parenthesisation**: binary operators always get parentheses, so nesting
  never changes precedence.
- **Immutability** of `FunctionCall`, `WindowSpec`, `CaseExpression`,
  `SortField`.

### Problems (the five known ones, confirmed, plus what the analysis found)

| # | Problem | Where |
|---|---|---|
| 1 | A `String` operand is rendered as SQL (`RenderContext.visit`). `eq(p.status, "ACTIVE")` compiles and becomes `p.STATUS = ACTIVE`. Almost every API takes `Object`. | `RenderContext`, `Conditions`, `Functions`, all builders |
| 2 | Columns are untyped (`Column implements Expression`). Nothing stops `eq(p.createdAt, "abc")`. | `table.Column` |
| 3 | Table definitions are written by hand, with no types, keys, nullability or defaults. | `TableDef` |
| 4 | No extension points: `returning`, `fetch`, `renderBody`, the clause lists are private. Integrations cannot see or change a statement. | `AbstractDml`, `AbstractSelect` |
| 5 | Global static executor with `ServiceLoader` discovery. | `SqlExecutors` |
| 6 | Scout remnants: `createContribution(..)` (two overloads), `query(Class)`, `Binds` returning `":p0"` strings that only work because strings are SQL, named `:name` placeholders with `.bind(name, value)`, the `qlid` live template. | `LxrinQL`, `bind.*`, `live-templates/` |
| 7 | Result mapping relies on reflection. Records are mapped **by position**, so reordering the select list silently breaks the mapping. Beans need aliases. | `ResultMapping` |
| 8 | `ResultMapping.convert` uses `ZoneId.systemDefault()` to move between `Instant`, `OffsetDateTime` and `LocalDateTime`. Results depend on the JVM's time zone. | `ResultMapping` |
| 9 | `in(col, list)` expands to one parameter per element, so the SQL text changes with the list size. That fills the statement cache and makes plans harder to reuse. | `Conditions.inCondition`, `NamedParameterSql` |
| 10 | Errors: one `SqlExecutionException` with a SQLSTATE. There is no way to tell a unique violation from a foreign-key violation without comparing strings. | `JdbcSqlExecutor` |
| 11 | Window frames, `LIMIT n`, `USING (..)` and CTE names are assembled from strings. | `WindowSpec`, `AbstractSelect` |
| 12 | Two builds (Maven and Gradle) that have to be kept in sync by hand. | `pom.xml`, `build.gradle.kts` |
| 13 | `Literal.toLiteral` quotes `toString()` of any unknown object. | `Literal` |
| 14 | JSON is always returned as `String`. There is no hook for typed JSON. | `JdbcSqlExecutor.readValue` |

Problems 1, 2 and 7 go to the core of the 2.x API. 3.0 is therefore a new API
rather than a refactoring of the old one. The rendering knowledge and the
function catalog are ported. The public surface is replaced.

## 2. Design principles

1. **A Java value is always a bind parameter.** No method outside
   `ch.lxrin.ql.dsl.Sql` writes a caller-supplied `String` into the SQL
   text. A `String` parameter is one of two things:
   - a **value**: it is bound, or written as an escaped literal where
     PostgreSQL requires a constant;
   - an **identifier** (alias, function name): it is validated against
     `[A-Za-z_][A-Za-z0-9_$]*` and quoted if necessary.

   Raw SQL goes only through `Sql.raw(..)` / `Sql.condition(..)` /
   `Sql.table(..)`. Those calls are easy to find with grep, and the
   `lxrin-ql-test` module has an ArchUnit rule that forbids them.
2. **Type errors are compile errors.** `USERS.CREATED_AT.gt(Instant)`
   compiles. `USERS.CREATED_AT.eq("abc")` does not, and neither does
   `USERS.EMAIL.plus(1)`.
3. **No silent meaning changes during migration.** Every 2.x construct whose
   meaning changes in 3.0 fails to compile in 3.0. This is the main reason
   why `Object`-typed operands are gone completely instead of being
   deprecated.
4. **Structure first, SQL last.** Statements are an inspectable model (an
   AST). Policies, conventions and listeners work on that model. Rendering
   to SQL happens once, at the end.
5. **No global state is required.** Everything hangs off a `QueryContext`.
   The static entry points (`Dsl.*`, `BEANS`) are thin facades over a
   default context or registry.
6. **The library stays general purpose.** Auditing, tenants, soft delete and
   "current user" are *examples* built on extension points. None of them is
   hard-coded.
7. **`lxrin-ql-core` has zero dependencies** and targets Java 17 (records and
   sealed interfaces yes; pattern-matching `switch` no).

## 4. Core type system

### 4.1 `DataType<T>` and converters

```java
public final class DataType<T> {
    String sqlName();              // "uuid", "timestamptz", "text[]", "app.role"
    Class<T> javaType();
    Kind kind();                   // STRING, NUMBER, TEMPORAL, BOOLEAN, JSON, ARRAY, BINARY, OTHER
    boolean sensitive();           // bind values are redacted in logs and exceptions

    <U> DataType<U> map(Class<U> type, Function<T, U> fromDb, Function<U, T> toDb); // value objects
    DataType<T[]> array();
    DataType<T> asSensitive();
}

public interface Converter<J, D> {            // for more complex cases than map(..)
    Class<J> javaType();
    DataType<D> databaseType();
    D toDatabase(J value);
    J fromDatabase(D value);
}
```

`SqlTypes` declares the built-in types. All of them are **zone-free**:
`Instant` ↔ `timestamptz` goes through `OffsetDateTime` in UTC, and
`LocalDateTime` ↔ `timestamp` is read and written as a `LocalDateTime`. The
JVM default zone is never used.

| `SqlTypes` constant | SQL | Java |
|---|---|---|
| `TEXT`, `VARCHAR`, `CITEXT` | text types | `String` |
| `INT2`, `INT4`, `INT8`, `NUMERIC`, `FLOAT4`, `FLOAT8` | numbers | `Short`, `Integer`, `Long`, `BigDecimal`, `Float`, `Double` |
| `BOOL` | `boolean` | `Boolean` |
| `UUID` | `uuid` | `UUID` |
| `DATE`, `TIME`, `TIMESTAMP`, `TIMESTAMPTZ`, `INTERVAL` | temporal | `LocalDate`, `LocalTime`, `LocalDateTime`, `Instant`, `Duration`/`PgInterval` |
| `JSONB`, `JSON` | JSON as text | `String` |
| `BYTEA` | `bytea` | `byte[]` |
| `pgEnum(name, E.class, labels)` | PostgreSQL enum | `E` (labels are configurable, e.g. `ADMIN` ↔ `admin`) |
| `enumAsText(E.class)` | text | `E` (stored by name) |
| `jsonb(T.class)` | `jsonb` | `T` via a `JsonCodec` registered in the context |

Value objects:

```java
public final class Types {
    public static final DataType<UserId> USER_ID =
            SqlTypes.UUID.map(UserId.class, UserId::new, UserId::value);
}
```

Enums, JSON and other PostgreSQL types that JDBC does not know are bound with
`setObject(i, text, Types.OTHER)`, so core does not need the PostgreSQL JDBC
driver at compile time.

`JsonCodec` is a small SPI (`String write(Object)`, `<T> T read(String, Type)`).
Core ships no implementation. `lxrin-ql-spring` registers a Jackson codec
automatically.

### 4.2 Fields, columns, conditions

```java
public interface Field<T> {                        // any typed SQL expression
    DataType<T> type();

    Condition eq(T value);        Condition eq(Field<T> other);
    Condition ne(T value);        Condition ne(Field<T> other);
    Condition gt / ge / lt / le  (T | Field<T>);
    Condition isNull();           Condition isNotNull();
    Condition isDistinctFrom(T | Field<T>);
    Condition in(Collection<? extends T> values);  // renders  x = ANY(?)  with one array bind
    Condition in(Select1<T> subQuery);
    Condition between(T from, T to);
    SortField<T> asc();  SortField<T> desc();
    Field<T> as(String alias);
    <U> Field<U> cast(DataType<U> type);
    Field<T> coalesce(T fallback);
}

public interface StringField  extends Field<String>  { like, ilike, startsWith, endsWith, contains, matches, concat, lower, upper, … }
public interface NumberField<N extends Number> extends Field<N> { plus, minus, times, divide, mod, neg, … }
public interface TemporalField<T> extends Field<T>   { plus(Duration), minus(Duration), truncate(DatePart), … }
public interface BooleanField extends Field<Boolean>, Condition { }
public interface JsonField<T> extends Field<T>       { get(String key), getText(String key), contains(T), hasKey(String), … }
public interface ArrayField<E> extends Field<E[]>    { contains(E...), overlaps(E...), any(), length(), … }

public interface Condition extends BooleanField {
    Condition and(Condition other);   Condition or(Condition other);   Condition not();
    static Condition noCondition();   // neutral element: skipped by and/or, WHERE TRUE when used alone
}
```

- `eq(null)` still throws. Use `isNull()` instead. `eqOrIsNull(T)` exists for
  "match this value or NULL" filters.
- `in(Collection)` binds **one array**, so the SQL is the same for 1 or 10 000
  values, and an empty collection simply matches nothing.
- `Column<T>` implements `Field<T>` and carries metadata: `table()`,
  `name()`, `nullable()`, `hasDefault()`, `generated()`, `identity()`. The
  specialised columns (`StringColumn`, `NumberColumn<N>`, …) implement the
  matching `…Field` interfaces. The code generator picks the column class from
  `DataType.kind()`.

### 4.3 Tables

```java
public abstract class Table<R extends Record> {
    String schema();  String name();  Optional<String> alias();
    List<Column<?>> columns();
    Optional<PrimaryKey<R, ?>> primaryKey();
    List<UniqueKey<R>> uniqueKeys();  List<ForeignKey<R, ?>> foreignKeys();
    Optional<Column<?>> column(String name);          // metadata lookup (not SQL), used by generic listeners
    RowMapper<R> rowMapper();                          // generated, no reflection
    abstract Table<R> as(String alias);                // generated: returns the concrete table class
    boolean readOnly();                                // views
}
```

### 4.4 Raw SQL: `Sql`

This is the only way to write SQL text. The result is still typed.

```java
Field<Double>  sim  = Sql.raw("similarity({0}, {1})", SqlTypes.FLOAT8, USERS.NAME, Sql.param(text));
Condition      c    = Sql.condition("{0} @@ websearch_to_tsquery('simple', {1})", DOCS.TSV, Sql.param(q));
Table<Row>     t    = Sql.table("legacy_import");            // ad-hoc table, columns via t.field("x", SqlTypes.TEXT)
```

Arguments are `Field`s (or `Sql.param(value)`), never strings. So even a raw
template cannot turn user input into SQL.

## 5. The DSL

The entry point is `import static ch.lxrin.ql.dsl.Dsl.*;` (statements run on
the default `QueryContext`) or an injected `QueryContext` (`ctx.select(..)`
has the same API).

### 5.1 SELECT with typed results

```java
// typed tuple
List<Row3<UUID, String, String>> rows = select(USERS.ID, USERS.NAME, USERS.EMAIL)
        .from(USERS)
        .where(USERS.EMAIL.endsWith("@gmail.com"))
        .orderBy(USERS.NAME.asc())
        .fetch();

// into your own record: the constructor reference is checked at compile time
record UserSummary(UUID id, String name, String email) {}
List<UserSummary> summaries = select(USERS.ID, USERS.NAME, USERS.EMAIL)
        .from(USERS)
        .fetch(UserSummary::new);

// whole table → generated row record
List<UserRow> all = selectFrom(USERS).where(USERS.DELETED_AT.isNull()).fetch();

// single values
Optional<String> name = select(USERS.NAME).from(USERS).where(USERS.ID.eq(id)).fetchOptional();
long n                = selectCount().from(USERS).where(USERS.ROLE.eq(Role.ADMIN)).fetchOne();
```

- `select(f1..fN)` returns `SelectN<T1..TN>` for N ≤ 16. These overloads are
  generated from a template in `build-logic`. `fetch()` returns
  `List<RowN<..>>`, and `fetch(MapperN)` takes a constructor reference.
- For more than 16 columns or a dynamic select list, `select(List<Field<?>>)`
  returns `Select<Row>`, and `row.get(USERS.NAME)` is still typed (`String`).
- Terminal operations: `fetch()`, `fetch(mapper)`, `fetchOne()` (exactly one
  row, else throws), `fetchOptional()`, `fetchFirst()`, `fetchCount()`,
  `fetchExists()`, `stream()` (cursor, must be closed), `fetchPage(..)`.
- Results are read with the declared `DataType` of each column
  (`rs.getObject(i, jdbcClass)` followed by the converter). There is no
  guessing from `ResultSetMetaData` and no reflection.

### 5.2 All 2.x SELECT features, typed

```java
UsersTable u = USERS.as("u");
OrdersTable o = ORDERS.as("o");

select(u.NAME, sum(o.TOTAL).filter(o.STATUS.eq(OrderStatus.PAID)).as("revenue"),
       rank().over(orderBy(sum(o.TOTAL).desc())))
    .from(u)
    .leftJoin(o).onKey(ORDERS.FK_USER)                 // join via generated foreign key
    .where(o.CREATED_AT.ge(now().minus(Duration.ofDays(365))))
    .groupBy(u.NAME)
    .having(sum(o.TOTAL).gt(new BigDecimal("1000")))
    .orderBy(field(3).desc())
    .limit(10)
    .fetch();
```

- Joins: `.join(t).on(cond)`, `.onKey(fk)`, `.using(col…)`, `leftJoin`,
  `rightJoin`, `fullJoin`, `crossJoin`, `lateral(subquery)`.
- CTEs: `CommonTable<Row2<UUID, BigDecimal>> paid = cte("paid", select(..))`,
  then `with(paid).select(paid.field(1))…` (typed CTE columns), plus
  `withRecursive`, `materialized()`, `notMaterialized()`, and data-modifying
  CTEs.
- Window specifications are typed:
  `rowsBetween(unboundedPreceding(), currentRow())` returns `FrameBound`
  objects instead of strings.
- Locking: `forUpdate().of(u).skipLocked()`. Set operations: `union`,
  `unionAll`, `intersect`, `except`, `…All`.
- `whereIf(boolean, Supplier<Condition>)` stays.

### 5.3 Keyset pagination

```java
Page<UserRow> page = selectFrom(USERS)
        .where(USERS.DELETED_AT.isNull())
        .orderBy(USERS.CREATED_AT.desc(), USERS.ID.desc())
        .seekAfter(lastCreatedAt, lastId)       // typed: must match the ORDER BY fields
        .limit(50)
        .fetchPage();                           // items + Optional<Cursor> next
```

When all sort directions are the same, `seekAfter` renders a row-value
comparison `(created_at, id) < (?, ?)`, which PostgreSQL can serve from an
index. With mixed directions it expands to the equivalent `OR` form.
`Cursor` can be encoded to and decoded from an opaque URL-safe string, for
REST APIs. Offset paging (`page(index, size)`) stays.

### 5.4 DML

```java
insertInto(USERS)
    .set(USERS.ID, UuidV7.generate())
    .set(USERS.NAME, "Ada")
    .set(USERS.EMAIL, "ada@example.org")
    .returning(USERS.CREATED_AT)
    .fetchOne();                                         // Instant

insertInto(USERS).columns(USERS.NAME, USERS.EMAIL)
    .values("Ada", "ada@example.org")                    // values(T1, T2) typed by columns(..)
    .values("Alan", "alan@example.org")
    .onConflict(USERS.EMAIL).doUpdate().setExcluded(USERS.NAME)
    .execute();

update(USERS).set(USERS.ROLE, Role.ADMIN).where(USERS.EMAIL.eq(mail)).execute();
update(USERS).set(USERS.LOGIN_COUNT, USERS.LOGIN_COUNT.plus(1)).where(..).execute();
deleteFrom(SESSIONS).where(SESSIONS.EXPIRES_AT.lt(Instant.now())).returning(SESSIONS.ID).fetch();
truncate(IMPORT_STAGING).restartIdentity().execute();
```

`UPDATE`/`DELETE` without `WHERE` is still rejected unless `.allRows()` is
called.

### 5.5 Functions and operators

The ~250 functions are ported with types, for example
`lower(Field<String>) → StringField`, `count() → NumberField<Long>`,
`sum(NumberField<Integer>) → NumberField<Long>`, `dateTrunc(DatePart, TemporalField<T>) → TemporalField<T>`
and `jsonbBuildObject(...) → JsonField<String>`. String constants such as
date fields become enums (`DatePart.MONTH`). Formats and patterns are
values: they are bound, or written as escaped literals where PostgreSQL needs
a constant.

User-defined functions and operators are typed and need no library change:

```java
public final class Pg {
    public static final Function2<String, String, Double> SIMILARITY =
            Functions.define("similarity", SqlTypes.TEXT, SqlTypes.TEXT, SqlTypes.FLOAT8);
    public static final BinaryOperator<Geometry, Geometry, Double> DISTANCE =
            Operators.binary("<->", Types.GEOMETRY, Types.GEOMETRY, SqlTypes.FLOAT8);
    public static final AggregateFunction1<BigDecimal, BigDecimal> MEDIAN =
            Functions.defineAggregate("my_schema.median", SqlTypes.NUMERIC, SqlTypes.NUMERIC);
}

select(USERS.NAME, Pg.SIMILARITY.call(USERS.NAME, param(q)).as("score")) ...
```

Names are validated identifiers (optionally schema-qualified). Operator
symbols are validated against PostgreSQL's operator character set. The code
generator can also emit such definitions for the database's own functions
(optional, see §8).

## 6. Runtime

### 6.1 `QueryContext`

```java
QueryContext ctx = QueryContext.builder()
        .dataSource(dataSource)                          // or .connectionProvider(..)
        .transactions(TransactionRunner.jdbc())          // default; Spring replaces it
        .types(t -> t.register(Types.USER_ID).jsonCodec(myCodec))
        .convention(ColumnConventions.createdAt("created_at", clock))
        .convention(ColumnConventions.updatedAt("updated_at", clock))
        .versionColumn("version")
        .policy(new SoftDeletePolicy("deleted_at", clock))
        .listener(new MyListener())
        .observer(new LoggingObserver(Duration.ofMillis(500)))   // System.Logger, no dependency
        .build();

QueryContext.setDefault(ctx);        // only for the static Dsl.* / BEANS facades
```

- A context is immutable and thread-safe. Create one per data source.
  `ctx.derive(b -> b.listener(..))` makes a variant.
- `ctx.select(..)`, `ctx.insertInto(..)` and so on produce **attached**
  statements. `Dsl.select(..)` produces **unattached** statements, which use
  `QueryContext.getDefault()` when they run. A statement can also be run with
  `stmt.attach(ctx)`.
- Policy bypass is explicit and easy to find:
  `ctx.bypassing(SoftDeletePolicy.class).select(..)`.

### 6.2 Execution SPI

```java
public interface SqlExecutor {
    QueryResult query(PreparedSql sql, List<DataType<?>> resultTypes);
    UpdateResult update(PreparedSql sql, List<DataType<?>> returningTypes);   // count + returned rows
    BatchResult batch(PreparedSql sql, List<List<Bind<?>>> rows, List<DataType<?>> returningTypes);
}
```

`PreparedSql` is SQL with `?` placeholders plus typed binds. The named
`:name` layer and `NamedParameterSql` are no longer needed. `JdbcExecutor`
is the implementation in core. Mocking is done with `lxrin-ql-test`'s
`MockExecutor` rather than by implementing JDBC.

### 6.3 Transactions

```java
public interface TransactionRunner {
    <T> T inTransaction(Propagation p, Supplier<T> work);   // REQUIRED, REQUIRES_NEW, NESTED (savepoint)
    Optional<TransactionScope> current();
}
public interface TransactionScope {
    <T> T attribute(Key<T> key, Supplier<T> ifAbsent);   // transaction-scoped storage, e.g. the audit revision id
    void afterCommit(Runnable r);  void afterRollback(Runnable r);
}

ctx.transaction(() -> { repo.save(a); repo.save(b); });          // REQUIRED
ctx.transaction(Propagation.REQUIRES_NEW, () -> ...);
```

- The core implementation binds the connection to the current thread, and
  nested calls use savepoints.
- The Spring implementation delegates to `PlatformTransactionManager` and
  stores attributes through `TransactionSynchronizationManager`.
- **Auto-transaction for writes with listeners.** If a write statement has an
  after-listener and no transaction is active, the pipeline wraps the
  statement and its listeners in one. For example, an audit row is never
  committed without its data row, or the other way round.

### 6.4 Errors

```

│   │   ├── NotNullViolationException         23502

│   ├── TransientDataAccessException
│   │   ├── SerializationFailureException     40001
│   │   ├── DeadlockException                 40P01

│   └── … others by SQLSTATE class

├── StaleEntityException                           update/delete matched 0 rows
│   └── OptimisticLockException                    version mismatch
└── InvalidStatementException                      e.g. UPDATE without WHERE
```

`UniqueViolationException.constraint()` returns the generated `UniqueKey`
(for example `USERS.UK_EMAIL`), so application code can react to "e-mail
already taken" without comparing strings.

### 6.5 Observability

```java
public interface ExecutionObserver {
    default void onStart(StatementEvent e) {}
    default void onSuccess(StatementEvent e, Duration took, long rows) {}
    default void onError(StatementEvent e, Duration took, LxrinQlException error) {}
}
// StatementEvent: kind, tables, sql(), binds() (sensitive values redacted), origin (DSL | repository method | listener)
```

Built-in observers:

- core: `LoggingObserver` (JDK `System.Logger`, slow-statement threshold,
  optional bind logging);
- spring: a Micrometer `Observation` observer when Micrometer is on the
  classpath, which gives metrics and tracing out of the box.

## 7. Statement pipeline and extension points

Every statement follows the same path, whether it comes from the DSL or from
a repository method:

```
build AST ─► policies ─► column conventions ─► listeners.before ─► render ─► observers.onStart
         ─► execute ─► observers.onSuccess/onError ─► listeners.after ─► map result for the caller
```

Listeners run in registration order (Spring: `@Order`). An exception in an
after-listener rolls back the transaction.

### 7.1 Statement listeners

```java
public interface StatementListener {
    default boolean appliesTo(Table<?> table) { return true; }

    default void beforeInsert(InsertContext c)     {}
    default void beforeUpdate(UpdateContext c)     {}
    default void beforeDelete(DeleteContext c)     {}
    default void beforeTruncate(TruncateContext c) {}

    default void afterInsert(WriteResult r)   {}
    default void afterUpdate(WriteResult r)   {}
    default void afterDelete(WriteResult r)   {}
    default void afterTruncate(TruncateResult r) {}
}
```

Before execution, a listener sees the **structure** of the statement and can
change it:

| Context | Can read | Can change |
|---|---|---|
| `InsertContext` | table, rows (`Map<Column, Field>` per row), `ON CONFLICT`, entity writes | `setValue(col, value)` on every row, `requestReturning(cols…)`, `reject(msg)` |
| `UpdateContext` | table, assignments, where condition, entity writes (old and new values) | `addAssignment(col, value)`, `addCondition(cond)`, `requestReturning(..)` |
| `DeleteContext` | table, where condition, entities | `addCondition(..)`, `requestReturning(..)` |
| `TruncateContext` | tables, flags | `reject(..)`, `captureRowsBeforeTruncate()` |

`EntityWrite` gives the entity and its `changes()`
(`Column → (old value, new value)`).

After execution, `WriteResult` provides:

- `affectedRows()`: rows with the columns requested through
  `requestReturning`, even when the caller asked for other `RETURNING` columns
  or none. The pipeline adds the requested columns to `RETURNING`, splits the
  result, and gives the caller only its own projection;
- `rowCount()`, `wasUpsert()`, and for upserts `inserted(row)`, computed from
  `(xmax = 0)`, which is added to `RETURNING` automatically;
- `dsl()`: a `QueryContext` bound to **the same connection and transaction**.
  Statements run through it go through the pipeline with
  `origin = LISTENER`, which lets a listener avoid recursion;
- `transaction()`: the `TransactionScope`, for transaction-level state such
  as one revision per transaction.

Limits in 3.0, stated openly:

- `TRUNCATE` cannot return rows. A listener can reject it or opt into
  `captureRowsBeforeTruncate()`, which runs `SELECT … FOR UPDATE` first.
- A data-modifying CTE whose table has a listener that needs affected rows is
  rejected with a clear error. Adding columns to a CTE's `RETURNING` could
  change the outer query. This can be lifted later.

### 7.2 Column conventions

```java
ctx.builder()
   .convention(ColumnConventions.onInsert("created_at", Instant.class, c -> clock.instant()))
   .convention(ColumnConventions.onInsert("created_by", String.class, c -> currentUser.get()))
   .convention(ColumnConventions.onInsertAndUpdate("updated_at", Instant.class, c -> clock.instant()))
   .convention(ColumnConventions.onInsertAndUpdate("updated_by", String.class, c -> currentUser.get()))
```

- A convention matches by column name across all tables, or by a predicate
  (`c -> c.table().schema().equals("app")`).
- The Java type is checked against the column's `DataType` when the context
  is built, so a misconfiguration fails at startup.
- A convention does not override a value the caller set explicitly, unless it
  is declared `forced()`.
- A convention can supply an expression instead of a Java value
  (`now()` / `clock_timestamp()`).
- **Version column:** `.versionColumn("version")`.
  - Entity updates render `SET version = version + 1 … WHERE id = ? AND version = ?`.
    If no row is affected, `OptimisticLockException` is thrown.
  - Bulk updates only increment the version.

### 7.3 Table policies

```java
public interface TablePolicy {
    boolean appliesTo(Table<?> table);
    default Condition filter(Table<?> table, PolicyContext c) { return Condition.noCondition(); } // every read and write
    default void onInsert(InsertContext c) {}                // e.g. set or validate organization_id
    default Statement onDelete(DeleteStatement d, PolicyContext c) { return d; }   // may rewrite
    default void onTruncate(TruncateContext c) {}            // e.g. reject
}
```

- `filter` is added for **every table reference**: `FROM`, joins (in the `ON`
  clause for outer joins, so a `LEFT JOIN` stays a left join), sub-queries,
  CTE bodies, and the `WHERE` of `UPDATE`/`DELETE`. It also applies to
  repository methods, because they use the same pipeline.
- Examples, shipped as ready-to-use classes because they are generic:
  - `SoftDeletePolicy("deleted_at")`: filter `deleted_at IS NULL`; `delete`
    becomes `UPDATE … SET deleted_at = now()`. Listeners see an `UPDATE`
    whose `originalKind()` is `DELETE`.
  - `TenantPolicy("organization_id", Supplier<UUID>)`: filter
    `organization_id = ?`, set on insert, reject a change of the tenant
    column, reject `TRUNCATE`.
- Bypass is explicit: `ctx.bypassing(TenantPolicy.class)` or
  `repo.bypassing(SoftDeletePolicy.class).findAll(..)`. An ArchUnit rule in
  `lxrin-ql-test` can restrict where `bypassing` may be used.
- Statements written with `Sql.raw` are not policy-aware. The architecture
  rule makes those places visible.

### 7.4 Custom types

Custom types are registered through `DataType` / `Converter` (§4.1). They
apply to bind parameters, result reading and entity fields alike, because all
three go through the column's `DataType`.

### 8.1 Source of the schema

`lxrin-ql-codegen` reads `pg_catalog` over JDBC (not only
`information_schema`, which lacks enums, identity details and comments). It
reads:

// User.java – mutable entity (§9)
// UserRepositoryBase.java – generated base (§10)

- **Key strategy** is derived from the schema:
  - `uuid` primary key → `uuidV7()`;
  - owned sequence or identity column → `sequence("app_user_id_seq")`
    (identity `ALWAYS` adds `OVERRIDING SYSTEM VALUE`);
  - otherwise none (natural or composite keys).

  Composite keys get a generated key record (`UserRoleKey`).
- Foreign keys become typed constants (`ORDERS.FK_USER`) for `onKey(..)` and
  for error mapping.
- Naming is handled by a `NamingStrategy` interface. The default rules
  (strip prefixes, singularise, `snake_case` → `camelCase`/`UPPER_SNAKE`) can
  be configured per table or column or replaced entirely.
- Tests use golden files: a fixed schema is generated and compared with
  checked-in expected sources, and the generated code is compiled in the test.

## 9. Entities

```java
public class User extends Entity<UserId> {         // generated; no annotations, no SQL
    private UserId id;  private String name;  private String email;  private Role role; ...

    public UserId getId() { return id; }
    public void setId(UserId id) { this.id = track(UsersTable.USERS.ID, this.id, id); }
    ...
}
```

`ch.lxrin.ql.entity.Entity<K>` (core) holds the tracking state. The public API
is read-only:

| Method | Meaning |
|---|---|
| `isNew()` / `isPersistent()` / `isDeleted()` | state; `new User()` is NEW; loaded or saved is PERSISTENT |
| `isChanged()` / `isChanged(Column)` | changed since creation or loading |
| `changes()` | `Map<Column<?>, Change<?>>` with the old and new value |
| `originalValue(Column<T>)` | value at load time |

Rules:

- A setter records a change only if the value really differs (`BigDecimal`
  is compared with `compareTo`, arrays with `Arrays.deepEquals`). Setting a
  field back to its original value removes the change.
- For a **new** entity, the tracked fields are exactly the columns that are
  inserted. Columns the application never set are left out, so database
  defaults apply, and `RETURNING` fills them in.
- State changes are **provisional until commit**. If the surrounding
  transaction rolls back, the entity goes back to its previous state and
  changes. Otherwise a rolled-back insert would leave an entity that believes
  it is persistent, and the next `save` would fail.
- Entities are plain mutable objects: identity `equals`, not thread-safe.
  `UserRow toRow()` and `static User from(UserRow)` convert between the two
  forms.

## 10. Repositories

```java
public abstract class UserRepositoryBase extends TableRepository<User, UserId, UsersTable> {

    public UserId createKey();                        // uuidV7() or nextval of the sequence
    public List<UserId> createKeys(int n);            // one round trip for sequences

    public User save(User e);                         // NEW → insert, PERSISTENT → update of changed columns
    public List<User> saveAll(Collection<User> es);   // one transaction, see below
    public User insert(User e);                       // force insert
    public User update(User e);                       // force update (NEW entity: all set columns)

    public void delete(User e);
    public void deleteById(UserId id);
    public int  deleteAll(Condition where);           // bulk, through the pipeline

    public Optional<User> findById(UserId id);
    public User           getById(UserId id);         // throws EntityNotFoundException
    public List<User>     findAll(Condition where, SortField<?>... orderBy);
    public Optional<User> findOne(Condition where);   // throws if more than one row
    public Page<User>     findPage(Condition where, PageRequest page);   // keyset or offset
    public boolean        exists(Condition where);
    public long           count(Condition where);

    public UserRepositoryBase bypassing(Class<? extends TablePolicy> policy);
    protected QueryContext ctx();                     // for custom queries in subclasses
}

public class UserRepository extends UserRepositoryBase {
    public UserRepository(QueryContext ctx) { super(ctx); }

    public Optional<User> findByEmail(String email) {
        return findOne(USERS.EMAIL.eq(email));
    }
    public List<UserSummary> admins() {
        return ctx().select(USERS.ID, USERS.NAME, USERS.EMAIL).from(USERS)
                .where(USERS.ROLE.eq(Role.ADMIN)).fetch(UserSummary::new);
    }
}
```

### Semantics

- **`save`**
  - The entity's tracked state decides between insert and update. Whether the
    id is set does not matter, because `createKey()` sets it before the first
    save.
  - An update writes only the changed columns (plus conventions and version).
    If nothing changed, no statement runs, and neither conventions nor
    listeners fire.
  - Entity writes always use `RETURNING *`. That picks up defaults, generated
    columns, trigger changes and convention values. It also gives
    listeners the full row at no extra cost.
  - After a successful save, the entity is PERSISTENT, its changes are reset,
    and a second `save` becomes an update.
- **`saveAll`**
  - Everything runs in one transaction (`Propagation.REQUIRED`): all rows are
    saved or none.
  - New entities → one multi-row `INSERT … VALUES (..), (..) RETURNING *`.
    Unset columns get `DEFAULT`, so rows with different column sets fit into
    one statement. The rows are split into chunks of at most
    `min(1000, 65535 / columns)`, because the PostgreSQL wire protocol allows
    at most 65535 bind parameters. Returned rows are matched to entities by
    primary key. Keys generated by the database fall back to the `VALUES`
    order. PostgreSQL keeps that order in practice, but it is not a
    documented guarantee, which is one more reason to prefer `createKey()`.
  - Persistent entities → grouped by the set of changed columns. Each group
    becomes one JDBC batch of identical `UPDATE … RETURNING *` statements.
    pgjdbc is expected to return the rows through `getGeneratedKeys`; this is
    verified in step 9. If it does not hold, the fallback is one
    `UPDATE … FROM (VALUES …)` statement per group. An update count of 0
    for any entity throws `StaleEntityException` or `OptimisticLockException`
    and rolls back the whole `saveAll`.
- **`update` / `delete`** of a row that is missing, was deleted meanwhile or
  is hidden by a policy throws `StaleEntityException`. With a version column,
  the version is part of the `WHERE` clause and a mismatch throws
  `OptimisticLockException`.
- All methods go through the pipeline (§7), so policies, conventions,
  listeners and observers apply to repositories and the DSL alike.
- Views get `ReadOnlyRepositoryBase`, which only has the `find…`, `exists`
  and `count` methods.

## 12. Spring integration

`lxrin-ql-spring`, Spring Boot 4 auto-configuration:

- **`QueryContext` bean** built from the `DataSource`. It uses a
  `ConnectionProvider` based on `DataSourceUtils`, so statements join
  `@Transactional` transactions, and a `TransactionRunner` backed by
  `PlatformTransactionManager`.
- **Beans of these types are collected automatically:** `StatementListener`,
  `TablePolicy`, `ColumnConvention`, `ExecutionObserver`, `DataType`,
  `QueryContextCustomizer`. They are ordered with `@Order`.
- **Repositories become beans**, through `@EnableLxrinRepositories` or the
  generated index. `QueryContext.setDefault(..)` and the `BEANS` delegate are
  set when the context refreshes and cleared when it closes.
- **Optional integrations:** a Jackson `JsonCodec` when Jackson is present,
  and a Micrometer `Observation` observer when Micrometer is present.
- **Properties** (`lxrin.ql.*`): slow-statement threshold, bind logging,
  `saveAll` chunk size.

"Current user" is not part of the library. The ISMS provides a
`Supplier<String>` that reads the Keycloak principal from Spring Security and
uses it in its conventions and listener.

## 14. Worked example: ISMS audit history

This lives in the ISMS, or in `integration-tests` as proof. It is **not**
part of the library. Requirement: every change to an audited table writes a
row to `<table>_aud`, linked to one `revision` row per transaction (who,
when). That includes rows written by `saveAll`, bulk `update(..)` and
`deleteAll(..)`.

```java
public final class AuditListener implements StatementListener {
    private static final TransactionScope.Key<Long> REVISION = TransactionScope.key("audit.revision");
    private final Map<Table<?>, Table<?>> audTables;     // built from the generated tables: USERS → USERS_AUD
    private final Supplier<String> currentUser;
    private final Clock clock;

    public boolean appliesTo(Table<?> t) { return audTables.containsKey(t); }

    public void beforeInsert(InsertContext c) { c.requestReturning(c.table().columns()); }
    public void beforeUpdate(UpdateContext c) { c.requestReturning(c.table().columns()); }
    public void beforeDelete(DeleteContext c) { c.requestReturning(c.table().columns()); }
    public void beforeTruncate(TruncateContext c) { c.reject("audited tables cannot be truncated"); }

    public void afterInsert(WriteResult r) { write(r, RevType.ADD); }
    public void afterUpdate(WriteResult r) { write(r, RevType.MOD); }
    public void afterDelete(WriteResult r) { write(r, RevType.DEL); }

    private void write(WriteResult r, RevType defaultType) {
        if (r.affectedRows().isEmpty()) return;
        long rev = r.transaction().attribute(REVISION, () ->
                r.dsl().insertInto(REVISION_T)
                        .set(REVISION_T.CREATED_BY, currentUser.get())
                        .set(REVISION_T.CREATED_AT, clock.instant())
                        .returning(REVISION_T.ID).fetchOne());
        Table<?> aud = audTables.get(r.table());
        InsertValuesStep insert = r.dsl().insertInto(aud).columns(aud.columns());
        for (AffectedRow row : r.affectedRows()) {
            RevType type = r.wasUpsert() ? (row.inserted() ? RevType.ADD : RevType.MOD) : defaultType;
            insert.valuesFrom(row, Map.of(aud.column("rev").orElseThrow(), rev,
                                          aud.column("revtype").orElseThrow(), type));
        }
        insert.execute();                 // same connection and transaction; *_aud tables are not audited, so no recursion
    }
}
```

This works only because of these extension points, and each is needed:

- structured before-hooks with `requestReturning`;
- affected rows independent of the caller's `RETURNING`;
- the same connection and transaction for `r.dsl()`;
- transaction-scoped attributes for one revision per transaction;
- auto-transaction for standalone writes;
- after-hook exceptions that roll back;
- soft delete visible to listeners as an `UPDATE` with `originalKind`.

`integration-tests` will contain this listener, and tests will prove all three
write paths (entity, `saveAll`, bulk DSL).

## 15. Breaking changes

3.0 is not source compatible with 2.x. By design (principle 3), all of the
following are **compile errors**, not behaviour changes.

| 2.x | 3.0 |
|---|---|
| artifact `ch.lxrin:lxrin-ql` | `ch.lxrin:lxrin-ql-core` (+ `-codegen`, `-gradle-plugin`, `-spring`, `-test`, `-bom`) |
| Maven + Gradle builds | Gradle only; Maven users consume the artifacts as usual and can run codegen via its CLI |
| `import static ch.lxrin.ql.LxrinQL.*` | `import static ch.lxrin.ql.dsl.Dsl.*` + generated `Tables.*` |
| hand-written `TableDef` / `Table` / `Column` | generated `Table<R>` with typed `Column<T>`; ad hoc: `Sql.table(..)` |
| `String` operand = SQL | a `String` is always a value; SQL only through `Sql.raw` / `Sql.condition` |
| `Object` operands everywhere | typed `Field<T>` / `T` |
| `val(x)`, `inline(x)` | not needed: `col.eq(x)` binds; `inline(x)` → `Dsl.inline(x)` (typed) |
| `raw`, `sql(template)`, `condition(String)`, `as(String, alias)` | `Sql.raw(template, type, args…)`, `Sql.condition(..)` |
| `Binds`, `BindMap`, `.bind(name, value)`, `:name` placeholders | removed |
| `createContribution(..)`, `query(Class)`, `select(Class, items…)` | `select(fields…)` + `fetch()` / `fetch(Mapper)` / `selectFrom(TABLE)` |
| `.multiple()`, `.single()` (null if none), `.optional()` | `.fetch()`, `.fetchOne()` (exactly one), `.fetchOptional()`, `.fetchFirst()` |
| `RowMapper` over `Object[]`, `ResultMapping` (reflection) | typed `RowN`, `MapperN`, generated row mappers; no reflection |
| `in(col, list)` → one bind per element | `col.in(list)` → `col = ANY(?)` |
| `LxrinQL.setDefaultExecutor`, `SqlExecutors`, `ServiceLoader` | `QueryContext` (+ `QueryContext.setDefault` for the static facade) |
| `SqlExecutor.select/execute(String, BindMap)` | `SqlExecutor.query/update/batch(PreparedSql, types)` |
| `JdbcSqlExecutor` | `JdbcExecutor` with `ConnectionProvider` / `TransactionRunner` |
| `SqlExecutionException` | `LxrinQlException` hierarchy with constraint-specific subclasses |
| window frame strings (`preceding(3)` returned `String`) | typed `FrameBound` |
| `dateTrunc("month", x)`, `extract("YEAR", x)` | `dateTrunc(DatePart.MONTH, x)`, `extract(DatePart.YEAR, x)` |
| `live-templates/LxrinQL.xml` (`qlid`) | removed |

Unchanged in spirit: every SELECT and DML clause and every catalog function
remains available, as do the rejection of `UPDATE`/`DELETE` without `WHERE`
and of `eq(null)`, and `whereIf`.

## 16. Migration path from 2.x

The goal is **incremental** migration, one repository or query at a time,
rather than one big switch.

1. **Coexistence.** Add `ch.lxrin:lxrin-ql-core:3.0.0` next to
   `ch.lxrin:lxrin-ql:2.0.0`. The packages do not overlap (§3), so both
   compile together. Both can share a transaction:
   - 2.x uses a `JdbcSqlExecutor(ConnectionProvider)` based on
     `DataSourceUtils`;
   - 3.0 uses the Spring `QueryContext`.
2. **Generate the schema.** Apply the Gradle plugin to the existing Flyway
   migrations. The generated tables replace the `TableDef` classes, which can
   stay until the last 2.x query using them is gone.
3. **Migrate queries file by file.** The compiler guides each step:

   | 2.x | 3.0 |
   |---|---|
   | `eq(p.status, val("A"))` | `P.STATUS.eq(Status.A)` |
   | `ge(p.age, 18)` | `P.AGE.ge(18)` |
   | `in(p.id, ids)` | `P.ID.in(ids)` |
   | `select(PersonDto.class, p.id, p.name).from(p).multiple()` | `select(P.ID, P.NAME).from(P).fetch(PersonDto::new)` |
   | `createContribution(Long.class).select(count()).from(p).single()` | `selectCount().from(P).fetchOne()` |
   | `.where("p.DELETED_AT IS NULL")` | `.where(P.DELETED_AT.isNull())`, or a `SoftDeletePolicy` |
   | `join("r", "r.ID = p.ID")` | a typed CTE / `onKey(..)`; as a last resort `Sql.condition(..)` |
   | `insertInto(p).set(p.name, val(n)).returning(p.id).single(Long.class)` | `insertInto(P).set(P.NAME, n).returning(P.ID).fetchOne()`, or a repository `save` |
   | `.executor(tx)` | `ctx.transaction(() -> ..)` / `@Transactional` |
   | `catch (SqlExecutionException e) if "23505".equals(e.getSqlState())` | `catch (UniqueViolationException e)` |
4. **Move CRUD to repositories** where it helps. Custom queries move into the
   hand-written repository subclasses.
5. **Remove `lxrin-ql` 2.x.** The ArchUnit rule `noRawSql()` then makes sure
   no string SQL comes back.

`docs/migration-2-to-3.md` will contain this guide in full, with a complete
table for every 2.x factory method (including all functions whose signature
changed).

## 18. Open questions

These need a decision before or during implementation. The recommendation
comes first.

1. **Result type of `select(a, b, c).fetch()`.** The target example shows
   `List<UserRow> rows = select(USERS.ID, USERS.NAME, USERS.EMAIL)…fetch()`.
   `UserRow` has all columns of the table, so a three-column select cannot
   produce it type-safely.
   - *Recommendation:* `fetch()` returns `List<Row3<…>>`;
     `fetch(UserSummary::new)` maps to your own record at compile time;
     `selectFrom(USERS).fetch()` returns `List<UserRow>`.
   - *Alternative:* a reflection-based `fetchInto(Class)` for records, matched
     by component name, as an opt-in convenience.
2. **Package names.** New packages that do not collide with 2.x, which
   enables side-by-side migration (recommended), or reuse of the 2.x package
   names (shorter imports, big-bang migration only)?
3. **Maven build.** I read the constraints as "Gradle only, remove
   `pom.xml`". The codegen CLI covers Maven consumers. Please confirm.
4. **Gradle plugin distribution.** Maven Central only, as the constraint says
   (consumers add `mavenCentral()` to `pluginManagement`), or also the Gradle
   Plugin Portal?
5. **Entity naming defaults.** Singularise table names (`users` → `User`)
   with simple English rules plus overrides (recommended), or keep the table
   name as is (`Users`)?
6. **Base class for entities.** Generated entities extend `Entity<K>` from
   core, which holds the tracking state (recommended: simple, and the entity
   has no SQL). Or should they be completely free of a base class, with
   tracking in a generated field and an accessor interface?

## 19. Decisions and deviations

### Decisions from the review (answers to §18)

1. No `fetchInto(Class)`: results are typed tuples (`RowN`), constructor references
   (`fetch(UserSummary::new)`) or generated row records (`selectFrom(USERS)`).
2. New packages that do not collide with 2.x, so both versions can run side by side.
3. The library is built with Gradle only (`pom.xml` removed). Maven projects are
   first-class consumers: `lxrin-ql-maven-plugin` (goal `generate`, bound to
   `generate-sources`) is built with Gradle from a hand-written plugin descriptor and
   shares `lxrin-ql-codegen` with the Gradle plugin. `integration-tests/consumers`
   contains an example Maven and an example Gradle project that are built against the
   fresh artifacts.
4. The Gradle plugin is published to Maven Central and to the Gradle Plugin Portal;
   the Maven plugin to Maven Central.
5. Table names are singularised by default, with per-table overrides and configurable
   prefixes to strip.
6. Generated entities extend `ch.lxrin.ql.entity.Entity<K>`.

### Where the implementation differs from the draft

| Draft | Implemented | Why |
|---|---|---|
| `Functions.define(..)`, `Operators.binary(..)` | `Routines.function(..)`, `Routines.aggregate(..)`, `Routines.operator(..)`, `Routines.conditionOperator(..)` | `Functions` is the catalog class inherited by `Dsl` |
| `.onConflict(..).doUpdate().setExcluded(..)` | `.onConflict(..).doUpdateSetExcluded(..)`, `.doUpdateSet(..)`, `.doUpdateWhere(..)` | keeps the 2.x vocabulary and one builder type |
| `cte("paid", select(..))` with `paid.field(1)` | `cte(..)` with `paid.field(queryField)` (by output name); recursive CTEs declare their columns (`declareNumber`, …) | typed without positional indexes |
| `seekAfter(..)` also for encoded cursors | `seekAfter(values…)`, `seekAfter(Cursor)`, `seekAfterCursor(String)` | with one `String` sort key, `seekAfter("m")` would have been ambiguous |
| `types(t -> t.register(..))` on the context builder | `jsonCodec(..)`; types are `DataType` constants, no registry | a registry was not needed: every field carries its type |
| Convention types checked when the context is built | checked when a convention first meets a column | the context does not know the tables in advance |
| Data-modifying CTEs rejected when listeners need affected rows | listeners do not see statements inside data-modifying CTEs | noted as a known limit; bulk DSL statements and repositories are fully covered |
| `saveAll` updates via `getGeneratedKeys` to be verified | verified: pgjdbc returns the `RETURNING` rows of JDBC batches | – |
| `lxrin-ql-test` rolls back after each test | also: transactions inside such a test become savepoints; `rollback = false` for real commits | one connection per test |
| Audit `<table>_aud` rows per change | one row per entity and revision; later changes in the same transaction update it (`ADD` stays `ADD`, `DEL` wins) | matches the primary key `(rev, id)` of Envers-style audit tables |
