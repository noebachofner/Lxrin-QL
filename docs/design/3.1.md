# LxrinQL 3.1 – Conditions and the createContribution style

Status: **implemented** in 3.1.0. This note records the decisions that 3.1 adds to the
[3.0 design](3.0.md). Nothing in the 3.0 API was removed or changed incompatibly.

## Goals

1. Conditions are complete, composable and dynamic, and every operator exists as a
   static function and as a field method.
2. The `createContribution(Type.class, TABLE, (c, b) -> …)` style is available again,
   as a thin layer over the 3.0 builders, and it is the primary style in the
   documentation.
3. Optional filters are explicit. `null` is never dropped silently.

## Decisions

| Topic | Decision | Reason |
|---|---|---|
| Where the static operators live | A new class `Conditions extends Values`; `Functions` now extends `Conditions`, and `Dsl` extends `Functions` | `import static …Dsl.*` keeps working. The methods that moved (`and`, `or`, `not`, `noCondition`, `exists`, `notExists`, `rangeContains`, `rangeOverlaps`, `tsMatches`) keep their signatures, and static calls still resolve through the subclasses, so the change is source and binary compatible. |
| Static vs. fluent | Each static function delegates to the field method | One implementation: the same SQL, binds and checks. |
| `null` values | Rejected by every operator, by `b.setX(..)` and by `ConditionBuilder`; `isDistinctFrom` and `eqOrIsNull` accept `null` on purpose | "Never dropped silently." |
| `null` conditions in `and(..)`/`or(..)` | Still skipped, as in 3.0; `where(..)`, `where(List)` and `ConditionBuilder` reject them | Changing `Condition.and(..)` would change the behaviour of 3.0 code; the new, recommended paths are strict. |
| Empty `in` | Stays one empty array parameter: `= ANY('{}')` is false, `<> ALL('{}')` true (also for NULL operands). Row values render `FALSE`/`TRUE` | The SQL text does not depend on the list size. |
| `ANY`/`ALL` | `Quantified<T>` as the right-hand side of the six comparisons; `eq(value, any(array))` binds the value with the element type | Covers every comparison without 12 extra method names. |
| Ranges and `tsvector` | New `RangeField`/`TsVectorField` interfaces, `RangeColumn`/`TsVectorColumn`, generated by codegen. `Fields.of(..)` returns them for range and `tsvector` types, so `tstzrange(..)` results are `RangeField`s at runtime; `range(..)`/`tsvector(..)` wrap any other expression | Fluent range operators without changing the declared return types of the 3.0 range functions (binary compatibility). |
| Row values | Untyped `RowValue` with arity and Java types checked when the condition is built | Typed `RowN` variants for 16 arities would add a lot of generated API for little gain. |
| `createContribution` | `c` is a `SelectScope<T>` whose `select(..)` returns a normal `Select<T>` with `FROM table` set; `createInsert`/`createUpdate`/`createDelete`/`createUpsert` pass the builder itself as `c`; `b` is `Binds` | A thin layer that shares the operators, type checks and pipeline of 3.0. |
| Result mapping | Records by component name (snake case = camel case, aliases allowed), otherwise by position; `Row`; or a single column type. Checked when the query is built | The class token of `createContribution` needs a runtime mapping. It is limited to records and checked early. There is still no general `fetchInto(Class)`. |
| `createUpsert` default | Without `onConflict(..)`: `ON CONFLICT (primary key) DO UPDATE SET` all other set columns from `EXCLUDED` (`DO NOTHING` if there are none) | The common upsert without boilerplate; an explicit `onConflict(..)` wins. |
| Sorting from requests | `Sorts.from(param, whitelist)`; unknown keys, directions or extra parts throw `InvalidSortException` | Nothing from the request reaches the SQL. |
| `UPDATE`/`DELETE` safety | Unchanged rule: the statement is rejected if its `WHERE` is `noCondition()` and `allRows()`/`all()` was not called. Junctions of only `noCondition()` collapse to it | Optional filters that are all absent can never update or delete every row by accident. |

## Tests

- `ConditionsTest`: every operator in both forms (SQL and binds), null rejection, deep
  nesting, `noCondition`, the builder, `when`/`…IfPresent`.
- `DynamicQueryTest`:
  - dynamic select lists, `orderBy(List)`, `Sorts` (including rejected parameters),
    `joinIf`, `setIf`/`setIfPresent`;
  - the rejection of `UPDATE`/`DELETE` statements that resolve to `noCondition()`;
  - the `createContribution` style: mapping, type errors, pipeline, and the same SQL
    as the `select` style.
- `ConditionsIT` (PostgreSQL via Testcontainers), one test per operator group:
  comparison, `BETWEEN`, `IN`/`ANY`/`ALL`/`EXISTS`, `NULL`/boolean, text, arrays,
  ranges, JSON, full-text search, row values, logic, dynamic filters, sorting, joins
  and writes in both styles. It runs against a new migration `V4__bookings.sql`
  (range, `tsvector`, `integer[]` and `jsonb` columns).
